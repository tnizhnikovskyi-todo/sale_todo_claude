# Конвенції репозиторію

Це маркетплейс плагінів Claude Code для фази продажів Odoo 19. Код тут — не програма,
а **скіли**: інструкції в `SKILL.md`, які Claude виконує.

## Перед будь-якою роботою над скілом

Прочитай три спільні контракти в `shared/` — вони обов'язкові, не довідкові:

- `shared/deal_journal_template.md` — журнал продажу, реєстри, ID, коефіцієнт
- `shared/registers.md` — регістри артефактів, Humizer, фільтр чутливого, межа дії
- `shared/skill_conventions.md` — вісім спільних конвенцій: приклади, мова, обсяг,
  ідемпотентність, збої, ліміти, погодження, evals
- `shared/handover_contract.md` — стик із треком впровадження

## Спільні файли

Правити **тільки** `shared/`. Копії в `plugins/*/skills/*/references/` генеруються
`scripts/sync-shared.sh` і несуть шапку «ЗГЕНЕРОВАНО». Довідники прикладів живуть
у `shared/examples/<імʼя-скіла>.md` і розкладаються за конвенцією імені, без мапи. Після зміни `shared/` —
перезапустити sync. `scripts/check-shared.sh` падає, якщо копію правили руками.

## Анатомія SKILL.md

Структура знята з наявних плагінів дому (`session-transcript-analyzer`,
`meeting-protocol-builder`) — не відступати від неї, інакше скіл не зростеться
з ланцюгом:

```
---
name: kebab-case-назва
description: >
  Запускай коли … Тригерні фрази — "…", "…". НЕ для X — для нього Y.
  Результат — `файл_[назва_компанії].md`.
---

# Title (англійською)

## Мета
## Інструменти та середовище      (читання · довідник · збереження · після завершення)
## Місце в потоці                  (попередник → цей скіл → наступник)
## Крок 0: Визнач вхідні дані      (поведінка на брак матеріалів)
## Крок 1…N
## Pre-save верифікація            (чекліст; для клієнтських — рядок «Humizer пройдено»)
## Шаблон                          (з плейсхолдерами [⚠️ ІНСТРУКЦІЯ: …])
## Наступний крок                  (дослівні тригерні фрази наступних скілів)
## Важливі правила
```

Обов'язково в кожному скілі:

- **Регістр кожного виходу оголошений** — машиночитний / внутрішній людський / клієнтський
- Негативні межі в `description` — «НЕ для X, для нього Y»
- «Не вигадуй» у Важливих правилах
- Для writers журналу — «Продовжуй ID, не перенумеровуй» і «Оновлюй на місці»

## Перевірки перед комітом

**Межа дії перевірок — `scripts/our-plugins.txt`.** Перевірки не глобують `plugins/*`,
а читають цей перелік: у спільному репозиторії методології поруч лежать плагіни інших
фаз, і глоб вимагав би від них наших конвенцій. Каталог плагінів задається змінною
`PLUGDIR` (типово `plugins`). Додаєш плагін фази — вносиш у перелік, інакше його
перевірки не побачать. Деталі переносу — `docs/migration-plan.md`.

```bash
./scripts/check-humizer.py <файл>  # клієнтський документ: ID, теги, механіка, жаргон
./scripts/check-shared.sh    # копії спільних контрактів не правили руками
./scripts/check-skills.sh    # SKILL.md тримають конвенції вище
./scripts/check-triggers.py  # тригерні фрази «Наступного кроку» = description цілі
./scripts/check-manifests.sh # манифести + власний валідатор Claude Code
./scripts/test-docx.sh       # конвейєр .docx: фікстури, негативні кейси, Humizer
./scripts/verify-install.sh   # маркетплейс ставиться з клону і плагіни несуть скіли
```

Те саме на кожен push виконує CI (`.github/workflows/checks.yml`), плюс перевірку,
що робочих артефактів із даними замовників у git немає.

Обидві падають з кодом 1 і переліком порушень. Чекер скілів — не формальність:
він ловить неоголошений регістр, скіл, не внесений у мапу регістрів, клієнтський скіл
без блокуючого Humizer, посилання на неіснуючий скіл і розходження дев'яти блоків
стику між `handover_contract.md` і скілом досьє. Він же викликає
`check-triggers.py`: фраза, якою один скіл радить викликати наступний, мусить існувати
дослівно в `description` цілі — інакше ланцюг виглядає цілим, а сейл диктує фразу
й нічого не отримує.

**Пастка «зеленої перевірки».** Двічі за ревʼю перевірка була зеленою й не працювала:
раз через SIGPIPE (нижче), раз через `sed`-діапазон без закриваючого рядка — він тягнув
файл до кінця, і під умову підпадали не ті скіли. Тому правило жорстке: **кожну
перевірку прогнати негативним тестом на кожному варіанті формулювання, яке вона
допускає**, і перевірити, скільком файлам вона взагалі адресована. Перевірка, що
адресована одному файлу з шести, — не перевірка.

**Пастка SIGPIPE.** Скрипти працюють під `set -o pipefail`, а `echo "$x" | grep -q …`
— це конвеєр, у якому `grep -q` виходить на першому збігу і `echo` отримує SIGPIPE
(код 141). `pipefail` віддає 141 як статус усього конвеєра, тому перевірка **іноді**
падає на цілком правильному файлі: приблизно один прогін із десяти, кожного разу
на іншому скілі. Тому в перевірках — **herestring `<<<"$x"`, а не конвеєр**; те саме
замість `ls … | head -1` (там під `set -e` падає вже весь скрипт). Фальшиве
падіння гірше за відсутню перевірку: воно вчить не вірити чекеру.

**Пастка локалі.** У цьому середовищі `LANG`/`LC_ALL` не виставлені, тому `grep` працює
в байтовому режимі, і **кириличні діапазони в дужках не збігаються**: `Регістр[иу]?`
не знайде «Регістри». Обидва скрипти тепер виставляють `LC_ALL=C.utf8`, але надійніше
писати альтернацію `(Регістр|Регістри)`, а не діапазон. Кожну нову перевірку
**обов'язково прогнати негативним тестом** — зелений чекер, який нічого не ловить,
гірший за відсутній.

## Чого не робити

- Не редагувати `plugins/*/skills/*/references/*` — це генеровані копії
- Не заводити свій формат журналу в окремому скілі — контракт один
- Не додавати скілу право надсилати листи, змінювати стадію угоди або писати в прод
