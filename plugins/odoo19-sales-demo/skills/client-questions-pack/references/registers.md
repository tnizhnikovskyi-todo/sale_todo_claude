# Регістри артефактів і Humizer

> Канонічне джерело: `shared/registers.md`. У плагіни потрапляє копією через
> `scripts/sync-shared.sh`. **Правити тільки тут.**

Кожен вихід кожного скіла має **оголошений регістр**. Неоголошений регістр —
скіл не готовий до публікації. Регістр належить **артефакту, не скілу**:
один скіл може віддавати виходи в різних регістрах.

---

## Навігація

| Розділ | Кому потрібен |
|--------|---------------|
| 1. Три регістри | усім — щоб оголосити регістр свого виходу |
| 1а. Мапа «скіл → вихід → регістр» | при додаванні нового виходу |
| 2. Мова за регістром | усім |
| 3. Humizer | тим, хто віддає **клієнтський** вихід |
| 4. Фільтр чутливого | тим, хто віддає клієнтський вихід, і аналітичним скілам |
| 5. Межа дії скіла | усім, хто пише в Odoo або надсилає щось |
| 5а. Де живуть артефакти | усім, хто зберігає файли |
| 6. Чого не вигадуємо | усім |

Читай **свої** розділи. Файл цілком потрібен лише при додаванні нового скіла.

## 1. Три регістри

### Регістр 1 — машиночитний

Читає наступний скіл, не людина.

| | |
|---|---|
| Що це | `журнал_продажу_[компанія].md` і все, що пише в його реєстри |
| Мова | технічна, ID обов'язкові |
| Humizer | **ЗАБОРОНЕНИЙ** — він прибирає ID, а вони тут єдиний носій трасування |
| Клієнту | ніколи |

Скіли: `brief-transcript-analyzer` · `data-completeness-scorer` · `demo-debrief` ·
`defence-debrief` · `handover-dossier-builder`

### Регістр 2 — внутрішній людський

Читає сейл або БА.

| | |
|---|---|
| Що це | документи на руки сейлу і БА |
| Мова | проста, мовою менеджера, без термінів Odoo де можливо |
| Що лишається | внутрішні маркери, ID, стоп-сигнали, ставка, білі плями, аргументація |
| Humizer | не застосовується — це не клієнтський документ |
| Клієнту | **ніколи**, навіть частинами |

Виходи: `Підготовка до брифу` · `Попередня оцінка` (з білими плямами) ·
`План демо-збірки` · `План проведення демо` (сценарій + стоп-сигнали + Q&A) ·
`Знімок демо-бази` · `Аргументація до захисту` · `Питання і побажання клієнта` ·
`Досьє передачі`

### Регістр 3 — клієнтський

Виходить за межі компанії.

| | |
|---|---|
| Що це | листи, оцінки, карта розривів, КП |
| Мова | мова замовника, стриманий діловий тон, «ви» |
| Humizer | **ОБОВ'ЯЗКОВИЙ І БЛОКУЮЧИЙ** |
| Надсилає | **сейл руками.** Скіл віддає чернетку і не надсилає нічого |

Виходи: `Чернетка follow-up після брифу` · `Чернетка follow-up після демо` ·
`Функціональні розриви` · `Оцінка проєкту` · `Оцінка дискавері` · `КП`

## 3. Humizer

Крок узятий з `meeting-protocol-builder` (плагін `odoo19-discovery-initiation`),
де він калібрований на 41 реальному протоколі EDELWEIS і польових правках методолога.
**Не переписуємо** — застосовуємо.

### Прибрати або перекласти

Англо-жаргон і кальки — пояснити в дужках при першій згадці або замінити:

| Було | Стало |
|------|-------|
| scope | обсяг / межі робіт |
| стейкхолдер | учасник / відповідальний |
| deliverable | результат |
| As-Is / To-Be | поточний / цільовий стан |
| pain points / bottleneck | вузькі місця |
| master data | основний довідник |
| Lead / Opportunity | лід / нагода |
| BoM / MO | специфікація / замовлення на виробництво |
| FIFO / FEFO / AVCO | пояснити принцип у дужках |

Канцелярит: «здійснюється» → робиться · «в розрізі» → за, по · «в частині» → щодо ·
«оптимізація витрат» → зменшення витрат.

### Прибрати повністю

- внутрішні маркери й **ID**: `Q-7`, `G-12`, `ST-3`, `[КО]`, 🔴
- метафори, образні порівняння, «образно кажучи»
- пряму мову і цитування учасників — тільки непряма або безособова форма
  («Замовник підтвердив…», «Було зазначено…»)
- розмовні довіски: «так зручніше рахувати», «по суті», «ваш зворотний зв'язок
  допомагає нам покращуватися»
- сліди транскрипту: «Speaker NN [хв:сек]», «fathom.video», таймкоди
- шаблонний boilerplate, однаковий між проєктами
- повторені copy-paste абзаци

### Зберегти точно

Дати, імена, домовленості, суми, рішення — без змін.

> **Точність важливіша за гладкість.** Humizer спрощує мову, не факти.

### Перевірка

Зрозуміє людина без IT-бекграунду? Немає жаргону і внутрішніх маркерів?
Немає метафор і розмовних вставок? Немає чутливого? Тон стриманий? Факти збережені?

У Pre-save верифікації клієнтського скіла — окремий рядок:
`- [ ] Humizer пройдено` — **«пройдено», не «врахувано»**.

### Механічна частина — `scripts/check-humizer.py`

Humizer доводився вичиткою, і саме тому протікав: на п'ятому документі підряд
формулювання з першого вже здаються нормальними. Тому частину, яку можна перевірити
машиною, перевіряє машина:

```
python3 scripts/check-humizer.py чернетка_джерело.md   # до складання .docx
python3 scripts/check-humizer.py документ.docx         # остання лінія перед клієнтом
```

**Що ловить:** ID реєстрів (`G-12`, `ST-3`), теги `[КО]`/`[ВО]`/`[ПП]`, маркери
рівня 🔴/🟡, сліди транскрипту (`Speaker 2`, таймкоди, `fathom.video`), механіку розрахунку
з §4 (коефіцієнт, ставка за годину, множник ×N, стоп-сигнали, білі плями) і всю
таблицю жаргону вище разом із канцеляритом.

**Чого не ловить і що лишається за людиною:** тон, метафори, розмовні довіски,
пряма мова, повторені абзаци — і головне питання «чи зрозуміє це людина без
IT-бекграунду». Перевірка **не заміняє Humizer**: вона ловить те, що прослизає.

Прогнана 19 негативними тестами (по одному на клас) і 7 позитивними — на тому, що
ловитись не мусить: «версія 2», «3-4 тижні», «22,40 € за користувача», «ставка
податку», «A4». На першому ж живому прогоні знайшла протік у документі, який уже
був позначений «Humizer пройдено»: «вартість уточнюється: ставку впровадження
визначає керівник проєкту» — тобто клієнтові показали механіку ціни.

## 4. Фільтр чутливого

Не виходить за межі компанії **ніколи**, у жодному документі регістру 3:

| Що | Чому |
|----|------|
| Сім стоп-сигналів і реєстр `ST-N` | список «за яких ознак ми не дістаємо КП» у клієнта = втрачена угода |
| Аргументація до захисту (`defence-brief`) | «на чому тримати лінію по ціні» — внутрішній документ за визначенням |
| **Ставка за годину** — будь-яка, і скільки б їх не було | клієнту йде тільки підсумок суми або вилки |
| **Коефіцієнт вилки ×1,5 / ×2 / ×3** | те, що верхня межа це нижня ×3, клієнт не бачить |
| Білі плями як перелік | у лист ідуть як запит даних, не як звіт про наші прогалини |
| Внутрішні практики й захисні умови виконавця | прибрані польовим тестом методолога |
| Внутрішні норми часу | те саме |

**Розведення з КП.** Правило 8 дому забороняє комерційні параметри в протоколі
«навіть як відкриті питання». КП і оцінки — виняток за призначенням: вони містять
**підсумкову суму або вилку**. Але не ставку, не коефіцієнт і не спосіб розрахунку.

Правильно в оцінці проєкту: `320–480 годин · 16 000–24 000 € без ПДВ`
Неправильно: `320 год × [ставка] €/год, верхня межа ×1,5 через неповноту даних`

**Цифр у листах немає взагалі.** Follow-up після брифу і після демо не містять
сум і вилок. Ціна живе тільки в КП і оцінках, які сейл показує усвідомлено.

## 5. Межа дії скіла

`odoo-connector` має право запису під ключем користувача. Тому межа проводиться
в скілах, а не в намірах.

| Дія | Можна |
|-----|-------|
| Записати у файл робочої папки | так |
| Записати в поля картки ліда або нагоди | так |
| Записати `lost_reason_id` при втраті | так, **тільки** `defence-debrief` і **тільки** після підтвердження сейлом. Значення — з довідника `crm.lost.reason`; вартісна причина **заборонена**, якщо клієнт ціни не бачив |
| Змінити стадію угоди | **ні** — гейт проходить людина |
| Створити активність або завдання з клієнтською видимістю | **ні** |
| Надіслати лист клієнту | **ні** — скіл віддає чернетку |
| Записати в демо-стенд | так, `demo-base-builder` |
| Записати в `erp.todo.ltd` або будь-який прод | **ні** |

`demo-base-builder` **перевіряє URL інстансу перед першим записом** і зупиняється,
якщо це прод. Це запобіжник у кроці скіла, не пункт політики.

Транскрипти й журнали не виходять за межі робочої папки та Odoo.
Жодних сторонніх сервісів.

## 5а. Де живуть артефакти — і чого немає в репозиторії

Усі виходи скілів — **робочі файли в робочій папці сейла**, а не файли репозиторію.
Репозиторій містить лише інструкції: `SKILL.md`, спільні контракти, анонімізовані
приклади.

| Що | Де живе | У git |
|---|---|---|
| журнал продажу, оцінки, КП, листи, знімки, досьє | робоча папка сейла | **ні** |
| транскрипти, анкети, матеріали клієнта | робоча папка, чатер картки | **ні** |
| `заперечення_[галузь].md` — накопичувальний | робоча папка | **ні** (містить формулювання клієнтів) |
| `SKILL.md`, `shared/*`, `scripts/*` | репозиторій | так |
| `shared/examples/*` — **анонімізовані** приклади | репозиторій | так |

**Чому це правило, а не звичка.** Журнал містить назву компанії, ПІБ, суми, обіцянки
й стоп-сигнали. Один комміт із таким файлом лишається в історії git назавжди —
видалення файлу наступним коммітом його не прибирає. Тому назви робочих артефактів
внесені в `.gitignore` шаблонами, а не тримаються на увазі.

**Якщо артефакт таки треба показати в репозиторії** (приклад для довідника) —
анонімізуй: «бухгалтерське бюро, мультикомпанійний облік, 5 користувачів» замість
назви; суми конкретних угод не переносяться взагалі. Галузь і масштаб — можна,
ідентифікація — ні.

## 6. Чого не вигадуємо

| Місце | Правило |
|-------|---------|
| Схожі клієнти | тільки факти з бази знань. **«Аналога немає» — валідна і достатня відповідь.** Вигадана схожість згорить при клієнті |
| Ліцензії Odoo | вносить сейл руками. Скіл не вигадує і не тягне з прайсу; неповнота видна в документі |
| Години | тільки історичний аналог × коефіцієнт, **аналог названий**. Цифра без джерела в оцінку не йде |
| **Ставка за годину** | живе в розділі 3 журналу, **ставить сейл**. Не вигадуємо, не тягнемо з прайсу, не переносимо з минулої угоди. Немає ставки — віддаємо вилку **в годинах** |
| Обіцянки продажника | фіксуються як прозвучали, у `P-N`, навіть нереалістичні. Реалістичність — окрема колонка |
| Будь-який факт | немає — «не вказано» + рядок у `Q-N` |

## 7. Мова

Замовчування — **українська**. Інша тільки коли сейл прямо просить: міжнародний лід,
англомовне демо, замовник без української.

- Канонічний правопис: **проєкт** (з єром) · **Odoo** — перша велика, решта малі
  (не ODOO, не odoo у тексті) · **бізнес-процес** через дефіс · **Discovery** латиницею
- Нормативна лексика: **торговельний** (не «торгівельний») · навчання (не «обучення») ·

- У документах-фактах — минулий час активного стану або безособово: «Домовились»,
  «Погодили», «Презентовано». Не «планується», не «буде зроблено»
