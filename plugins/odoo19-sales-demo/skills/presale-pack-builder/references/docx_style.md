# Фірмовий стиль клієнтських документів (.docx)

> Канонічне джерело: `shared/docx_style.md`. У плагіни потрапляє копією через
> `scripts/sync-shared.sh`. **Правити тільки тут.**

Чотири клієнтські документи — **функціональні розриви, оцінка проєкту, оцінка
дискавері, КП** — віддаються замовнику як **`.docx`**, а не як `.md`. Це не питання
формату файлу: документ, який клієнт відкриває у Word, він читає як документ компанії,
і його вигляд є частиною пропозиції.

Стиль **знятий із реального КП ToDo** (будівельна компанія, перший етап: маркетинг
і продажі) — не вигаданий. Усі значення нижче виміряні у файлі, а не підібрані на око.

---

## Навігація

| Розділ | Кому потрібен |
|--------|---------------|
| 1. Як складається документ | усім, хто віддає клієнтський документ |
| 2. Стиль: шрифти, кольори, сторінка | при сумніві, як має виглядати |
| 3. Розмітка для `make-docx.py` | під час написання документа |
| 4. Скелет КП | `presale-pack-builder`, `offer-finalizer` |
| 5. Скелети трьох інших документів | ті самі два скіли |
| 6. Pre-save для `.docx` | перед віддачею файлу |

---

## 1. Як складається документ

Скіл **не збирає XML руками** і не вигадує форматування. Порядок такий:

```
1. пишемо зміст у markdown-підмножині (розділ 3)     → чернетка_[документ].md
2. проходимо Humizer                                  → блокуючий, за registers.md §3
3. python3 scripts/make-docx.py чернетка.md вихід.docx --title "…"
4. python3 scripts/check-docx.py вихід.docx           → дев'ять перевірок стилю
5. чернетку .md лишаємо поряд                         → з неї перевипускають версію
```

**Чернетка `.md` — не сміття, а джерело.** `offer-finalizer` перевипускає документ
із неї, а не парсить `.docx`. Тому чернетка зберігається під тим самим імʼям
із суфіксом `_джерело.md`.

**Візуальної перевірки в нашому середовищі немає** — LibreOffice тут не завантажує
файли, тому `check-docx.py` перевіряє структуру: шрифт, кеглі, кольори, шапку таблиці,
поля сторінки, колонтитули, залишені плейсхолдери. Перший документ по новому клієнту
**сейл відкриває у Word сам** — про це сказано в підсумку скіла.

## 2. Стиль: шрифти, кольори, сторінка

Виміряно у зразку: **1452 прогони з 1497 — Arial**. Мішанина Cambria/Times
у стилях зразка — слід копіювання з веба, а не рішення; відтворювати її не треба.

| Елемент | Значення |
|---------|----------|
| Основний шрифт | **Arial**, 12 pt (`w:sz` 24), міжрядковий 1,15 |
| Титул документа | Arial **bold 36 pt**, по центру |
| Заголовок розділу (H1) | Arial bold 16 pt, колір **`#ED7D31`**, по центру |
| Підзаголовок (H2) | Arial bold 13 pt, колір `#ED7D31`, зліва |
| Заголовок 3-го рівня | Arial bold 12 pt, чорний |
| Заголовок 4-го рівня | Arial *курсив* 12 pt, чорний |
| Маркери списку | `●` перший рівень, `▪` другий, `◦` третій |
| Таблиця | рамки 0,5 pt, шапка **`#FE5000`** білим жирним, вирівнювання клітинок по центру вертикалі |
| Виноска (`>`) | тло `#F2F2F2`, ліва оранжева лінія |
| Сторінка | A4, поля: верх 2,25 см · низ 1,5 см · ліво 2,5 см · право 1 см |
| Шапка сторінки | логотип + `м. Київ, вул. Центральна, 21 · +38 073 871 53 13 · sale@todo.ltd · www.todo.ltd` |
| Перша сторінка | **без шапки** (`titlePg`), з логотипом у тілі |
| Колонтитул | номер сторінки |

Два оранжевих — не помилка: `#ED7D31` у заголовках, `#FE5000` у шапках таблиць.
Так у зразку, і так лишається.

**Чого в цих документах немає ніколи** — за `registers.md` §3 і §4: жодного ID
(`G-12`, `Q-7`, `P-1`), тегів `[КО]`/`[ВО]`/`[ПП]`, ставки, коефіцієнта, механіки
розрахунку, `ST-N`, `R-N`, назв інших клієнтів. `check-docx.py` ловить залишені
плейсхолдери, решту — Humizer.

## 3. Розмітка для `make-docx.py`

```
[[LOGO]]                     логотип ToDo по центру
# Комерційна пропозиція       титул
## 1. Про Odoo                заголовок розділу, оранжевий, центр
### 2.1. Швидкий старт        підзаголовок, оранжевий
#### CRM та клієнти           заголовок 3-го рівня
##### Деталізація             заголовок 4-го рівня, курсив
звичайний абзац
- пункт                       маркер ●
  - підпункт                  маркер ▪ (два пробіли)
1. пункт                      нумерований
| Етап | Години |             таблиця
|---|---|                     рядок-роздільник обов'язковий
| Discovery | 50–100 |
> текст                       виноска
---                           тонка оранжева лінія
[[PAGEBREAK]]                 розрив сторінки
**жирний** *курсив*           усередині будь-якого рядка
```

Усе інше скрипт **не приймає**: падає з номером рядка. Це свідомо — тиха втрата
розмітки в клієнтському документі дорожча за помилку в консолі.

Ширини колонок таблиці рахуються з довжини вмісту; вручну їх не задають.

## 4. Скелет КП — структура зразка, дослівно

Порядок розділів **не переставляти й не скорочувати**: він відпрацьований на живих
угодах. Розділи, для яких немає даних, лишаються з рядком «уточнюється на Discovery»,
а не зникають.

```
[[LOGO]]
# Комерційна пропозиція
   підзаголовок: на що саме (компанія, етап: що входить)
   контакти компанії одним рядком

Шановні партнери та замовники!
   подяка за звернення + що включає ця пропозиція

#### Про компанію Замовника
#### Виклики та проблеми              ← списком, словами клієнта
#### Цілі впровадження                ← списком, з підпунктами
#### Очікуваний результат             ← списком

## 1. Про Odoo
   що це, спільнота, готові інтеграції в Україні, міжнародний досвід

## 2. Концепція проєкту впровадження
### 2.1. Швидкий старт                ← чому спершу Discovery
### 2.2. Концепція реалізації         ← версія Odoo, склад рішення
#### Функціональні області впровадження
   ##### CRM та управління клієнтами  ← блоками, у кожному 3–7 пунктів
   ##### Продажі
   ##### Маркетинг
   ##### Фінанси
   ##### Інтеграції
   ##### Комунікації та спільна робота
#### Що не входить у цей етап          ← з X-N, як межа етапу
#### Результат впровадження

## 3. Вартість і терміни реалізації
### Вартість ліцензій Odoo             ← ціна за користувача, розрахунок на N осіб
### Вартість послуг упровадження       ← таблиця: Етап | Обсяг робіт, години | Вартість, EUR без ПДВ
   останній рядок таблиці — «Разом по всім етапам»
### Порядок розрахунків                ← Time & Material: як платимо, як звітуємо
### Discovery: що це і що ви отримуєте ← перелік документів на виході
### Терміни реалізації                 ← таблиця: Етап | Термін
> Пропозиція дійсна до [дата]

#### Наступний крок                    ← одна дія з датою

[[PAGEBREAK]]
## Про компанію ToDo
   роки досвіду · розмір команди · кількість упроваджень · галузі · переваги
#### Контакти
```

**Що в цьому скелеті обов'язкове й найчастіше губиться:**
- **«Що не входить у цей етап»** — без цього розділу межа етапу неузгоджена,
  і це майбутній спір про scope;
- **рядок «Разом по всім етапам»** — клієнт шукає його першим;
- **«Пропозиція дійсна до»** — конкретна дата, за замовчуванням 30 днів;
- **«Порядок розрахунків»** — модель T&M проговорюється до підписання, не після;
- **вартість ліцензій Odoo окремо від послуг** — це різні рядки бюджету, і ліцензії
  вносить сейл (див. `deal_journal_template.md`, розділ 3).

## 5. Скелети трьох інших документів

Стиль **той самий** — шрифт, кольори, таблиці, колонтитули. Різна тільки структура.

### Функціональні розриви

```
[[LOGO]]
# Функціональні розриви
   компанія · дата · версія
Про що цей документ            ← 2–3 речення: що таке розрив, звідки перелік
## 1. Розриви за напрямами
### [Напрям]                    ← таблиця: Вимога (як поведінка) | Як покриваємо | Год. від | Год. до
   «Як покриваємо» — клієнтською мовою: налаштування / доробка / інтеграція
## 2. Що не входить у цей етап   ← з X-N
## 3. Що уточнюється на Discovery ← білі плями без ID і без тегів
> Оцінка попередня; уточнюється після обстеження.
```

### Оцінка проєкту

```
[[LOGO]]
# Оцінка проєкту
   компанія · дата · версія
## 1. Обсяг робіт               ← таблиця: Напрям | Що входить | Год. від | Год. до
## 2. Вартість                  ← таблиця: рядок робіт, рядок ліцензій, рядок «Разом»
## 3. Умови                     ← T&M, порядок оплати, що входить у гарантію
## 4. Терміни                   ← таблиця: Етап | Термін
> Чому вилка широка — одним реченням про уточнення на Discovery. Без механіки.
```

### Оцінка дискавері

```
[[LOGO]]
# Оцінка передпроєктного обстеження
   компанія · дата · версія
## 1. Навіщо обстеження         ← що воно знімає: ризик, розкид оцінки
## 2. Склад робіт               ← таблиця: Крок | Що робимо | Год.
## 3. Хто працює                ← ролі, БЕЗ конкретних імен
## 4. Що ви отримуєте            ← перелік документів на виході
## 5. Вартість і терміни        ← таблиця
#### Наступний крок
```

**Ролі без імен** — правило `registers.md` §4: конкретні люди в клієнтських
документах не називаються, бо склад команди на момент старту може змінитись.

## 6. Pre-save для `.docx`

Ці рядки йдуть у чекліст кожного скіла, що віддає клієнтський документ:

- [ ] Чернетка `.md` збережена поряд із `.docx` — із неї перевипускають версію
- [ ] `make-docx.py` пройшов без помилок; жодного рядка розмітки не втрачено
- [ ] `check-docx.py` — **дев'ять перевірок зелені**
- [ ] Humizer пройдено **до** складання `.docx`, не після
- [ ] У документі немає жодного ID, тега, ставки, коефіцієнта, `ST-N`, `R-N`
- [ ] Таблиця вартості має рядок «Разом»; у КП є «Пропозиція дійсна до»
- [ ] Розділ «Що не входить у цей етап» присутній і не порожній
- [ ] У підсумку сказано сейлу **відкрити файл у Word** перед відправкою —
      візуального рендеру в скіла немає
