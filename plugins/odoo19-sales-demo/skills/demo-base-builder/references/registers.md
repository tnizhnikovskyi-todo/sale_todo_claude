# Регістри артефактів і Humizer

> Канонічне джерело: `shared/registers.md`. У плагіни потрапляє копією через
> `scripts/sync-shared.sh`. **Правити тільки тут.**

Кожен вихід кожного скіла має **оголошений регістр**. Неоголошений регістр —
скіл не готовий до публікації. Регістр належить **артефакту, не скілу**:
один скіл може віддавати виходи в різних регістрах.

---

## Навігація

| Розділ | Кому потрібен |
|--------|---------------|
| 1. Три регістри | усім — щоб оголосити регістр свого виходу |
| 1а. Мапа «скіл → вихід → регістр» | при додаванні нового виходу |
| 2. Мова за регістром | усім |
| 3. Humizer | тим, хто віддає **клієнтський** вихід |
| 4. Фільтр чутливого | тим, хто віддає клієнтський вихід, і аналітичним скілам |
| 5. Межа дії скіла | усім, хто пише в Odoo або надсилає щось |
| 5а. Де живуть артефакти | усім, хто зберігає файли |
| 6. Чого не вигадуємо | усім |
| 7. Мова | усім, хто пише людині; клієнтським — разом із §3 |

Читай **свої** розділи. Файл цілком потрібен лише при додаванні нового скіла.

## 1. Три регістри

### Регістр 1 — машиночитний

Читає наступний скіл, не людина.

| | |
|---|---|
| Що це | `журнал_продажу_[компанія].md` і все, що пише в його реєстри |
| Мова | технічна, ID обов'язкові |
| Humizer | **ЗАБОРОНЕНИЙ** — він прибирає ID, а вони тут єдиний носій трасування |
| Клієнту | ніколи |

Скіли: `brief-transcript-analyzer` · `data-completeness-scorer` · `demo-debrief` ·
`defence-debrief` · `handover-dossier-builder`

### Регістр 2 — внутрішній людський

Читає сейл або БА.

| | |
|---|---|
| Що це | документи на руки сейлу і БА |
| Мова | проста, мовою менеджера, без термінів Odoo де можливо |
| Що лишається | внутрішні маркери, ID, стоп-сигнали, ставка, білі плями, аргументація |
| Humizer | не застосовується — це не клієнтський документ |
| Клієнту | **ніколи**, навіть частинами |

Виходи: `Підготовка до брифу` · `Попередня оцінка` (з білими плямами) ·
`План демо-збірки` · `План проведення демо` (сценарій + стоп-сигнали + Q&A) ·
`Знімок демо-бази` · `Аргументація до захисту` · `Питання і побажання клієнта` ·
`Досьє передачі`

### Регістр 3 — клієнтський

Виходить за межі компанії.

| | |
|---|---|
| Що це | листи, оцінки, карта розривів, КП |
| Мова | мова замовника, стриманий діловий тон, «ви» |
| Humizer | **ОБОВʼЯЗКОВИЙ І БЛОКУВАЛЬНИЙ** |
| Надсилає | **сейл руками.** Скіл віддає чернетку і не надсилає нічого |

Виходи: `Чернетка follow-up після брифу` · `Чернетка follow-up після демо` ·
`Функціональні розриви` · `Оцінка проєкту` · `Оцінка дискавері` · `КП`

## 2. Скіли з мішаним пакетом

`presale-pack-builder` віддає п'ять документів у двох регістрах одночасно.
Скіл зобов'язаний оголосити регістр кожного:

| Документ | Регістр |
|----------|---------|
| План презентації (сценарій + стоп-сигнали + Q&A) | **2 — внутрішній** |
| Функціональні розриви | 3 — клієнтський |
| Оцінка проєкту | 3 — клієнтський |
| Оцінка дискавері | 3 — клієнтський |
| КП | 3 — клієнтський |

`offer-finalizer` — те саме: чотири фінальні документи клієнтські, запис суми
в поля Odoo — регістр 1.

## 3. Humizer

Крок узятий з `meeting-protocol-builder` (плагін `odoo19-discovery-initiation`),
де він калібрований на 41 реальному протоколі EDELWEIS і польових правках методолога.
**Не переписуємо** — застосовуємо.

### Прибрати або перекласти

Англо-жаргон і кальки — пояснити в дужках при першій згадці або замінити:

| Було | Стало |
|------|-------|
| scope | обсяг / межі робіт |
| стейкхолдер | учасник / відповідальний |
| deliverable | результат |
| As-Is / To-Be | поточний / цільовий стан |
| pain points / bottleneck | вузькі місця |
| master data | основний довідник |
| Lead / Opportunity | лід / нагода |
| BoM / MO | специфікація / замовлення на виробництво |
| FIFO / FEFO / AVCO | пояснити принцип у дужках |

Канцелярит: «здійснюється» → робиться · «в розрізі» → за, по · «в частині» → щодо ·
«оптимізація витрат» → зменшення витрат · «з метою» → щоб · «у випадку, якщо» → якщо ·
«надається можливість» → можна · «вищезазначений» → цей.

Кальки з російської й англійської — таблиця нижче. Ліва колонка — точні форми, які
ловить `check-humizer.py`:

| Було | Стало | Рівень |
|------|-------|--------|
| слідуючий · являється · в залежності від · на даний момент · по питанню · приведений нижче · згідно графіку (без «з») · задавати питання · заключається · приймати міри · співставити · до цих пір · учбовий · по мірі · прийдеться | наступний · є · залежно від · зараз · з питання, щодо · наведений нижче · згідно з графіком · ставити питання · полягає · вжити заходів · зіставити · досі · навчальний · у міру · доведеться | помилка |
| діючий · існуючий · керуючий · бажаючі · оточуючий · працюючий · блокуючий · визначаючий · завершуючий | чинний · наявний · керівний · охочі · навколишній · робочий · блокувальний · визначальний · завершальний | помилка |
| приймати участь · на протязі · співпадати · являє собою | брати участь · протягом · збігатися · є | попередження |
| в кінці дня · робити різницю · на щоденній основі · імплементувати · адресувати проблему · додавати цінність · дайте знати | зрештою · мати значення · щодня · впровадити · розвʼязати · бути корисним (і сказати чим) · повідомте | попередження |
| у якості · дякуючи · по відношенню до | як · завдяки · щодо | попередження — бувають законні: «в якості збірки», «дякуючи вам за…» |

Польських калік («в годинах», «під адресою») не ловимо: «вилка **в годинах**» у нас
законна і правильна, а аудиторія польських калік не пише.

### Переписати

- **Пасив із виконавцем → актив.** «Договір підписується директором» → «Договір підписує
  директор». Безособове «-но/-то» без виконавця лишається: «Погоджено», «Було зазначено» —
  норма протоколу (див. «Прибрати повністю», пряма мова)
- **«X, а не Y» підсумком абзацу і «не просто X, а Y»** — хід, яким модель закриває
  думку. Замість протиставлення — сам факт: «Залишок видно в момент операції»
- **Заголовок «Висновок» над переказом** сказаного вище — прибрати. Висновок лишається,
  тільки якщо додає нове: рішення, строк, наступний крок
- Порожні зачини «варто зазначити», «важливо розуміти», «не секрет, що» — прибрати.
  **«Варто + дієслово дії»** («варто перевірити залишки до запуску») — нормальна форма
  поради, її не чіпаємо
- Штампи без факту: «комплексний підхід», «надійний партнер», «команда професіоналів»,
  «широкий спектр», «на новий рівень». Або факт («12 впроваджень в оптовій торгівлі»),
  або нічого

### Прибрати повністю

- внутрішні маркери й **ID**: `Q-7`, `G-12`, `ST-3`, `[КО]`, 🔴
- метафори, образні порівняння, «образно кажучи»
- пряму мову і цитування учасників — тільки непряма або безособова форма
  («Замовник підтвердив…», «Було зазначено…»)
- розмовні довіски: «так зручніше рахувати», «по суті», «ваш зворотний зв'язок
  допомагає нам покращуватися»
- сліди транскрипту: «Speaker NN [хв:сек]», «fathom.video», таймкоди
- шаблонний boilerplate, однаковий між проєктами
- повторені copy-paste абзаци

### Зберегти точно

Дати, імена, домовленості, суми, рішення — без змін.

> **Точність важливіша за гладкість.** Humizer спрощує мову, не факти.

- **Не посилювати твердження.** «Може скоротити час на звірку» не стає «скорочує», «частково
  покривається стандартом» не стає «покривається». Для КП це головний ризик: посилене
  твердження клієнт потім предʼявить як обіцянку
- **Не вигадувати деталей заради живості.** Олюднення — це мова, не нові факти
- Термін не заміняти близьким словом: «ліцензія» не «підписка», «Замовник» не «клієнт»

### Перевірка

Зрозуміє людина без IT-бекграунду? Немає жаргону і внутрішніх маркерів?
Немає метафор і розмовних вставок? Немає чутливого? Тон стриманий? Факти збережені?
Жодне твердження не стало сильнішим, ніж у джерелі? Слово не прибране лише тому, що
трапилось один раз у переліку, — а голос ШІ не замінений голосом «гуманайзера»?

У Pre-save верифікації клієнтського скіла — окремий рядок:
`- [ ] Humizer пройдено` — **«пройдено», не «врахувано»**.

### Механічна частина — `scripts/check-humizer.py`

Humizer доводився вичиткою, і саме тому протікав: на п'ятому документі підряд
формулювання з першого вже здаються нормальними. Тому частину, яку можна перевірити
машиною, перевіряє машина:

```
python3 scripts/check-humizer.py чернетка_джерело.md   # до складання .docx
python3 scripts/check-humizer.py документ.docx         # остання лінія перед клієнтом
```

Два рівні: **✗ помилка** — документ клієнту не йде (код 1); **⚠ попередження** —
друкується, код 0, рішення за людиною: «в рамках договору» в договірній частині КП —
норма жанру.

**Помилки:** ID реєстрів (`G-12`, `ST-3`), теги `[КО]`/`[ВО]`/`[ПП]`, маркери
рівня 🔴/🟡, сліди транскрипту (`Speaker 2`, таймкоди, `fathom.video`), механіка розрахунку
з §4 (коефіцієнт, ставка за годину, множник ×N, стоп-сигнали, білі плями), таблиця
жаргону вище і «здійснюється / в розрізі / в частині». Форма письма з §7: латиниця або
ы/э/ъ/ё всередині кириличного слова, невидимі символи (U+00AD, U+200B, U+FEFF…),
апостроф не `ʼ`. Однозначні русизми й дієприкметники на -учий/-ючий з таблиці калік.
Бот-хвости: «Сподіваюся, це допоможе», «не соромтеся звертатися», «Чудове запитання!».

**Мʼякий старт мовних правил.** Чужі букви, невидимі символи, апостроф не `ʼ`, русизми,
дієприкметники на -учий/-ючий і бот-хвости спершу лише попереджають, а з дати
`STRICT_FROM` у `check-humizer.py` блокують (рішення власника 2026-11-04). Дата живе
тільки в чекері; кожне таке попередження друкує, з якого дня воно стане помилкою,
тож не відкладай його виправлення: після цієї дати той самий документ не пройде.
ID, теги, рівні, сліди транскрипту, механіка ціни й жаргон блокують завжди.
`--today РРРР-ММ-ДД` підміняє сьогоднішню дату — це для тестів, не для обходу.

**Канал листа: `--channel email`.** Чернетку листа сейл копіює в пошту, і лист іде
звичайним текстом: `**жирне**` там лишиться зірочками. Тому для листа Markdown-розмітка
в тілі — **помилка** (блокує одразу, мʼякого старту немає): `**`, `__`, `#` на початку
рядка, чекбокс `- [ ]`, зворотні лапки, таблиця (`|---|` або рядок, що починається
з `|`). Звичайний перелік через `- ` — не розмітка, у листі він читається.
Тіло листа — між маркерами шаблону:

```
<!-- ↓↓↓ ТІЛО ЛИСТА ПОЧИНАЄТЬСЯ ТУТ ↓↓↓ -->
…текст, який сейл копіює в пошту…
<!-- ↑↑↑ ТІЛО ЛИСТА ЗАКІНЧУЄТЬСЯ ТУТ ↑↑↑ -->
```

Шапка чернетки вище тіла (Кому, Тема) розмітку мати може, але решту правил проходить:
тема йде клієнту. Блок «Для сейла» нижче кінцевого маркера клієнту не йде і не
перевіряється. У документах `.md` і `.docx` (канал за замовчуванням) розмітка — не
помилка: `.md` складається в `.docx`, і `**` там стає жирним.

```
python3 scripts/check-humizer.py --channel email лист_після_демо_[компанія].md
```

**Попередження:** кальки з рівнем «попередження», канцелярит («з метою», «в рамках»,
«наступні:»), штампи ШІ, тире-зʼєднувач після жирної назви, дефіс або «–» з пробілами
між словами, прямі лапки, діапазон через дефіс («3-4 тижні»).

**Чого не ловить і що лишається за людиною:** тон, метафори, розмовні довіски,
пряма мова, повторені абзаци, пасив із виконавцем, «X, а не Y», посилені твердження —
і головне питання «чи зрозуміє це людина без IT-бекграунду». Перевірка **не заміняє
Humizer**: вона ловить те, що прослизає.

**Межі мовних правил** — уроки чужих детекторів, на яких ті хибили в діловому тексті:
тільки точні форми, без стемінгу («функціонал» не падає через «функціонувати»);
апостроф — частина слова («зʼявляється» не ловиться як «являється»); діапазон «від 320
до 480 годин» — не штамп. Списки калік, дієприкметників, штампів і бот-хвостів узяті як
мовні дані з `panchlab/humanizer-uk` (MIT) і `git-voitenko/anti-ai-slop-writing` (MIT);
атрибуція — у шапці `check-humizer.py`. Кейси «мусить упасти / не мусить» —
`tests/humizer/cases.txt`, прогін — `scripts/test-humizer.py`.

Внутрішнє й чутливе прогнане 19 негативними тестами (по одному на клас) і 7 позитивними
— на тому, що ловитись не мусить: «версія 2», «3–4 тижні», «22,40 € за користувача»,
«ставка податку», «A4» (`scripts/test-docx.sh`). Мовні правила — негативним кейсом на
кожну словоформу (1 158), 75 ручними негативними, 63 позитивними, 13 брудними й 4 чистими
фікстурами; сам тест перевірений 18 мутаціями чекера (`tests/humizer/mutate.py`) —
кожна його валить. На першому ж живому прогоні знайшла протік у документі, який уже
був позначений «Humizer пройдено»: «вартість уточнюється: ставку впровадження
визначає керівник проєкту» — тобто клієнтові показали механіку ціни.

## 4. Фільтр чутливого

Не виходить за межі компанії **ніколи**, у жодному документі регістру 3:

| Що | Чому |
|----|------|
| Сім стоп-сигналів і реєстр `ST-N` | список «за яких ознак ми не дістаємо КП» у клієнта = втрачена угода |
| Аргументація до захисту (`defence-brief`) | «на чому тримати лінію по ціні» — внутрішній документ за визначенням |
| **Ставка за годину** — будь-яка, і скільки б їх не було | клієнту йде тільки підсумок суми або вилки |
| **Коефіцієнт вилки ×1,5 / ×2 / ×3** | те, що верхня межа це нижня ×3, клієнт не бачить |
| Білі плями як перелік | у лист ідуть як запит даних, не як звіт про наші прогалини |
| Внутрішні практики й захисні умови виконавця | прибрані польовим тестом методолога |
| Внутрішні норми часу | те саме |

**Розведення з КП.** Правило 8 дому забороняє комерційні параметри в протоколі
«навіть як відкриті питання». КП і оцінки — виняток за призначенням: вони містять
**підсумкову суму або вилку**. Але не ставку, не коефіцієнт і не спосіб розрахунку.

Правильно в оцінці проєкту: `320–480 годин · 16 000–24 000 € без ПДВ`
Неправильно: `320 год × [ставка] €/год, верхня межа ×1,5 через неповноту даних`

**Цифр у листах немає взагалі.** Follow-up після брифу і після демо не містять
сум і вилок. Ціна живе тільки в КП і оцінках, які сейл показує усвідомлено.

## 5. Межа дії скіла

`odoo-connector` має право запису під ключем користувача. Тому межа проводиться
в скілах, а не в намірах.

| Дія | Можна |
|-----|-------|
| Записати у файл робочої папки | так |
| Записати в поля картки ліда або нагоди | так |
| Записати `lost_reason_id` при втраті | так, **тільки** `defence-debrief` і **тільки** після підтвердження сейлом. Значення — з довідника `crm.lost.reason`; вартісна причина **заборонена**, якщо клієнт ціни не бачив |
| Змінити стадію угоди | **ні** — гейт проходить людина |
| Створити активність або завдання з клієнтською видимістю | **ні** |
| Надіслати лист клієнту | **ні** — скіл віддає чернетку |
| Записати в демо-стенд | так, `demo-base-builder` |
| Записати в `erp.todo.ltd` або будь-який прод | **ні** |

`demo-base-builder` **перевіряє URL інстансу перед першим записом** і зупиняється,
якщо це прод. Це запобіжник у кроці скіла, не пункт політики.

Транскрипти й журнали не виходять за межі робочої папки та Odoo.
Жодних сторонніх сервісів.

## 5а. Де живуть артефакти — і чого немає в репозиторії

Усі виходи скілів — **робочі файли в робочій папці сейла**, а не файли репозиторію.
Репозиторій містить лише інструкції: `SKILL.md`, спільні контракти, анонімізовані
приклади.

| Що | Де живе | У git |
|---|---|---|
| журнал продажу, оцінки, КП, листи, знімки, досьє | робоча папка сейла | **ні** |
| транскрипти, анкети, матеріали клієнта | робоча папка, чатер картки | **ні** |
| `заперечення_[галузь].md` — накопичувальний | робоча папка | **ні** (містить формулювання клієнтів) |
| `SKILL.md`, `shared/*`, `scripts/*` | репозиторій | так |
| `shared/examples/*` — **анонімізовані** приклади | репозиторій | так |

**Чому це правило, а не звичка.** Журнал містить назву компанії, ПІБ, суми, обіцянки
й стоп-сигнали. Один комміт із таким файлом лишається в історії git назавжди —
видалення файлу наступним коммітом його не прибирає. Тому назви робочих артефактів
внесені в `.gitignore` шаблонами, а не тримаються на увазі.

**Якщо артефакт таки треба показати в репозиторії** (приклад для довідника) —
анонімізуй: «бухгалтерське бюро, мультикомпанійний облік, 5 користувачів» замість
назви; суми конкретних угод не переносяться взагалі. Галузь і масштаб — можна,
ідентифікація — ні.

## 6. Чого не вигадуємо

| Місце | Правило |
|-------|---------|
| Схожі клієнти | тільки факти з бази знань. **«Аналога немає» — валідна і достатня відповідь.** Вигадана схожість згорить при клієнті |
| Ліцензії Odoo | вносить сейл руками. Скіл не вигадує і не тягне з прайсу; неповнота видна в документі |
| Години | тільки історичний аналог × коефіцієнт, **аналог названий**. Цифра без джерела в оцінку не йде |
| **Ставка за годину** | живе в розділі 3 журналу. **Базова ставка впровадження — 50 €/год**, і її скіл підставляє сам, назвавши це в документі. Інших ставок не вигадуємо, з прайсу не тягнемо, з минулої угоди не переносимо. Ставка дискавері базової не має — питаємо. Сейл сказав «ставка інша», але не назвав — вилка **в годинах** |
| Обіцянки продажника | фіксуються як прозвучали, у `P-N`, навіть нереалістичні. Реалістичність — окрема колонка |
| Будь-який факт | немає — «не вказано» + рядок у `Q-N` |

## 7. Мова

Замовчування — **українська**. Інша тільки коли сейл прямо просить: міжнародний лід,
англомовне демо, замовник без української.

- Канонічний правопис: **проєкт** (з єром) · **Odoo** — перша велика, решта малі
  (не ODOO, не odoo у тексті) · **бізнес-процес** через дефіс · **Discovery** латиницею
- Нормативна лексика: **торговельний** (не «торгівельний») · навчання (не «обучення») ·
  наступний (не «слідуючий»)
- **Одна мова на документ.** Мішана українсько-російська — дефект, ловиться на Pre-save
  і чекером: російські ы/э/ъ/ё і латинська «о» в кириличному слові — помилка
- **Апостроф один — `ʼ` (U+02BC)**, стандарт дому. Не `'` і не `’`: два види в одному
  документі видно в Word, а прямий `'` ламає пошук. Чекер вважає інший апостроф
  всередині слова помилкою
- **Звертання — кличним відмінком:** «Пане Андрію», «Шановна Олено Петрівно».
  Одна форма на документ — «ви» (§1), без переходів на «ти» чи безособове в листі
- Типографіка: лапки «ялинки», тире «—» між словами, «–» без пробілів у діапазоні
  («3–4 тижні», «320–480 годин»); якщо член діапазону сам із пробілом — з пробілами
  («3 600 – 7 200», «3 тижні – 1,5 місяці»)
- «Замовник» і «Виконавець» з великої як **сторони договору**.
  Але **«клієнт» не чіпаємо**, коли це кінцевий покупець Замовника («картка клієнта»,
  «клієнт оплатив», ліди) — суцільна заміна хибно спрацьовує
- У документах-фактах — минулий час активного стану або безособово: «Домовились»,
  «Погодили», «Презентовано». Не «планується», не «буде зроблено»
- Терміни — **конкретна дата** (ДД.ММ.РРРР), не «найближчим часом». Псевдостроки —
  перший маркер слабкого документа
