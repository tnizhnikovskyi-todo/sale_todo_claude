# ToDo · Odoo 19 · Продажі (фаза 0)

Маркетплейс із трьох плагінів, які закривають **фазу продажів** — ланку, якої немає
перед наявним ланцюгом методології Odoo 19. Сьогодні цей ланцюг починається з того,
що БА розбирає листування від продажника; після цієї фази він отримує структуру.

```
► ФАЗА 0 ПРОДАЖІ  →  Ініціація  →  Дискавері  →  Завершення  →  ТР  →  MVP/білд  →  Go-live
  (цей репозиторій)   discovery-    discovery-   discovery-    tr-      mvp-build   implementation
                      initiation    sessions     closeout      authoring
```

Носій стану, який фаза віддає далі: `журнал_продажу_[компанія].md` → `досьє_передачі_[компанія].md`
→ вхід у `sales-handover-analyzer`.

## Як поставити

> **Команді ToDo робити нічого не потрібно.** Маркетплейс методології підключений
> централізовано в Organization settings — плагіни фази продажів приходять разом
> із рештою методології.

Якщо потрібно поставити вручну — з маркетплейсу методології, **не з цього репозиторію**:

```bash
claude plugin marketplace add todoltd/claude-methodology-marketplace
claude plugin install odoo19-sales-prep@todo-odoo19-methodology
claude plugin install odoo19-sales-demo@todo-odoo19-methodology
claude plugin install odoo19-sales-offer@todo-odoo19-methodology
```

У TUI те саме робиться через `/plugin`. Оновити —
`claude plugin marketplace update todo-odoo19-methodology`.

Плагіни можна ставити окремо: `prep` працює самостійно, `demo` очікує журнал
від `prep`, `offer` — журнал і пакет від попередніх двох.

**Фаза переїхала.** Каталоги трьох плагінів і спільні частини лежать у
`todoltd/claude-methodology-marketplace`; імені маркетплейсу `todo-odoo19-sales`
більше немає — залишилось `todo-odoo19-methodology`. Цей репозиторій лишається
**джерелом розробки**: тут `shared/` як джерело правди, перевірки, фікстури й звіти
прогонів, а `.claude-plugin/marketplace.json` тримається тільки для CI (парність
версій і `claude plugin validate`). Ставити з нього не треба.

Синхронізація в маркетплейс методології — `.github/workflows/sync-to-methodology.yml`;
порядок і пастки описані в `docs/migration-plan.md`.

**Установка перевіряється скриптом, не на слово** — `./scripts/verify-install.sh`
(є в CI). Він клонує закоммічене дерево, ставить три плагіни й перевіряє чотири речі:
кількість скілів у кеші дорівнює кількості в дереві, інструментарій у кеші **побайтово
дорівнює** тому, що в коміті, конвейєр `.docx` збирається з каталогу встановленого
скіла — без доступу до кореня репозиторію, — і скільки це коштує контексту.

Дві причини, чому цього не заміняє `claude plugin validate`:

- установка вміє написати `√ Successfully installed` і дати **нуль скілів** — заміряно;
- **`claude plugin marketplace remove` кеш не чистить**, тому повторний прогін
  у тому самому контейнері читає стару версію і рапортує зеленим. Скрипт піднімає
  власний `HOME`, тому міряє завжди свіжий вміст і не торкається справжнього `~/.claude`.

**Межа цієї перевірки.** Вона ставить із **цього** маркетплейсу, а команда ставить
із маркетплейсу методології. Тому зелений тут означає «фаза не зламана й готова
до синхронізації», а **не** «у команди все встане»: приймання установки — на боці
цілі, після мержу. `verify-install.sh` і `check-manifests.sh` — джерельні за
призначенням: у дереві цілі вони не падають, а свідомо пропускаються з поясненням.

**Ціна контексту** (заміряно `claude plugin details`): три плагіни разом додають
**≈ 6 000 токенів** у кожну сесію — це тільки описи, за якими Claude вибирає скіл.
Сам скіл коштує 7,4k–12,0k токенів у момент виклику. Ліміт `SKILL.md` — 550 рядків,
його тримає `./scripts/check-skills.sh`.

**Авторам** перед комітом: `claude plugin validate .` і `claude plugin validate plugins/<плагін>`
— це власний валідатор Claude Code, він перевіряє манифести, скіли, агенти
й команди. Обидва виклики загорнуті в `./scripts/check-manifests.sh`.

## Спільні контракти

Три файли в `shared/` — **єдине джерело істини**. Читати перед написанням будь-якого скіла.

| Файл | Що фіксує |
|------|-----------|
| `shared/deal_journal_template.md` | журнал продажу: реєстри `D/X/G/Q/C/P/ST/R/A`, інваріанти ID, формула коефіцієнта вилки, алгоритм reconcile, шаблон, типи полів `crm.lead` |
| `shared/registers.md` | три регістри артефактів, мапа «скіл → вихід → регістр», Humizer, фільтр чутливого, межа дії скіла, чого не вигадуємо |
| `shared/skill_conventions.md` | девʼять спільних конвенцій: довідник прикладів · мова за регістром · обсяг виходу · ідемпотентність · поведінка при збої · ліміти входу · фіксація погодження · калібрування опису · що читати з довідників |
| `shared/handover_contract.md` | стик із треком впровадження: дев'ять блоків `sales-handover-analyzer` і джерело кожного |
| `shared/docx_style.md` | фірмовий стиль клієнтських `.docx`: шрифт, кольори, сторінка, розмітка для `make-docx.py`, скелет КП зі зразка і скелети трьох інших документів |
| `shared/examples/<скіл>.md` | довідник прикладів кожного скіла — розкладається в його `references/examples.md` за конвенцією імені, без мапи |

Скіл читає ці контракти зі свого `references/`. Копії **генеруються** — правити
можна тільки `shared/`.

```bash
./scripts/sync-shared.sh    # розкласти копії по скілах
./scripts/check-shared.sh   # перевірити, що копії не правили руками
./scripts/check-skills.sh   # перевірити SKILL.md на конвенції дому
./scripts/check-manifests.sh # манифести узгоджені між собою і з деревом каталогів

python3 scripts/make-docx.py чернетка.md вихід.docx --title "…"   # зібрати клієнтський .docx
python3 scripts/check-docx.py вихід.docx                          # перевірити стиль .docx
./scripts/test-docx.sh                                            # прогнати конвейєр на фікстурах
```

**Чотири клієнтські документи** — функціональні розриви, оцінка проєкту, оцінка
дискавері, КП — віддаються замовнику у **`.docx`** фірмовим стилем. Стиль знятий
із реального КП компанії (Arial, заголовки `#ED7D31`, шапка таблиці `#FE5000`,
A4 з фірмовими полями, шапка сторінки з логотипом), скелет КП — теж зі зразка.
Шаблон пакета живе в `assets/docx-template/`; поряд із кожним `.docx` лишається
чернетка `_джерело.md`, з якої перевипускають наступну версію.

**Стабільні блоки КП** — «Про Odoo», «Про компанію ToDo», загальні контакти — лежать
в `assets/docx-boilerplate/` і вставляються директивою `[[INCLUDE:шлях]]` дослівно.
У них цифри-факти (600+ у R&D Odoo, 53 000 додатків, 65+ співробітників,
40+ упроваджень, третє місце в рейтингу партнерів), і переказ таких цифр своїми
словами — це округлення або тихе завищення. Змінились факти — правиться один раз
у файлі, а не в кожному КП.

**Анкета стадії Qualified** — `assets/questionnaire/анкета.md`. Сім розділів
відповідають блокам відкритих питань журналу один в один, а розділ 7 — трьом умовам
доступу з формули коефіцієнта. Заповнена анкета збиває коефіцієнт напряму; збирає
й надсилає її `client-followup-writer` листом після брифу.

`./scripts/test-docx.sh` прогоняє конвейєр на чотирьох фікстурах (`tests/docx/`)
плюс анкету **із самого шаблона**, і на 14 негативних кейсах: непідтримувана розмітка
мусить падати з номером рядка, зламаний стиль — ловитись перевіркою. Плюс два
регресійні кейси на дефекти, знайдені анкетою: жирний через розрив рядка і порожня
таблиця-форма.

Мапа «файл → скіли» — у `scripts/shared-map.txt`.

`check-skills.sh` ловить механічно те, що інакше ловилось би на око: відсутність
негативної межі в `description`, неоголошений регістр, скіл, не внесений у мапу
регістрів, брак розділу «Не вигадуй», шаблон без плейсхолдерів
`[⚠️ ІНСТРУКЦІЯ: …]`, клієнтський скіл без рядка чеклісту `- [ ] Humizer пройдено`,
відсутній `references/examples.md`, скіл, який читає журнал без контракту журналу,
writer журналу без інваріантів ID, блок «Довідники», що не називає розділів,
розходження формули коефіцієнта з контрактом і посилання на неіснуючий скіл.
Окремо повідомляє, скільки довідників прикладів досі заготовки.

**29 перевірок, і кожна прогнана негативним тестом.** Це не формальність: двічі
за роботу перевірка була зеленою й не працювала — раз через SIGPIPE під `pipefail`,
раз через `sed`-діапазон без закриваючого рядка, який робив writer'ом кожен скіл,
що згадує журнал. Обидві пастки описані в `CLAUDE.md`.

## Три правила, які тримають усе

1. **ID наскрізні й вічні.** `G-12` із журналу продажу доїжджає до `AC-01` у ТР і далі
   до акта приймання тим самим `G-12`. Перенумерував — розірвав трасування безшумно.
2. **Регістр оголошений у кожного виходу.** Машиночитний / внутрішній людський /
   клієнтський. Для клієнтського Humizer обов'язковий і блокуючий. Регістр належить
   артефакту, не скілу: `presale-pack-builder` віддає п'ять документів у двох регістрах.
3. **Скіл нічого не надсилає і не проходить гейти за людину.** Листи — чернетки;
   стадію угоди змінює сейл; у прод-базу скіл не пише ніколи.

**Усі 18 скілів написані і проходять `check-skills.sh`.** Перший прогін на живій
угоді пройдено частково — звіт у `docs/dry-run-01.md`. Він знайшов один серйозний
дефект (ставка була захардкоджена у 12 місцях) і дві структурні знахідки
(транскрипти лежать у чатері картки; транскрипт може не мати дати). Усі три виправлені.

**Ревʼю 16 скілів дало 193 рекомендації; закрито 193.** Чотири фази:
системні дірки → в контракти (`shared/skill_conventions.md`), критичні → у скіли,
суттєві → у скіли, дрібні → у скіли плюс наскрізна прив'язка кожного Pre-save
до §2 мови, §3 обсягу і §4 ідемпотентності. Звіти по фазах — у `docs/dry-run-01.md`.

**Аудит 03 звірив скіли з живою базою** і знайшов чотири дефекти, яких ревʼю
не бачило, бо всі вони про розбіжність із базою, а не про якість тексту: домен
виграних угод повертав чужі угоди (у стадії Won 161 угода, наших 78); історія втрат
читалась порожньою (втрату оформлюють архівуванням, і Odoo архівні записи
за замовчуванням не віддає); таблиця стадій журналу не мала Proposition, Won
і Postponed; записи скілів у картку були невидимі. Звіт — `docs/dry-run-01.md`.

Чого досі немає:
- **повного прогону.** Жоден скіл не запускався на справжньому транскрипті брифу
  як файлі, на заповненій анкеті й на стенді;
- **довідників прикладів із реального прогону** — 13 із 18 лишаються заготовками.
  Заповнювати їх вигаданими прикладами заборонено конвенцією: такий файл гірший
  за відсутній;
- **прогону евалів.** Кейси на всі 18 описів написані — `docs/eval-routing-cases.md`;
  `claude plugin eval` у нашому середовищі відповідає «early access».

Вхід у ланцюг — `brief-prep-pack` («підготуй до брифу»). Далі кожен скіл сам
називає наступний у розділі «Наступний крок».

План хвиль — в артефакті «Обв'язка воронки продажів».
